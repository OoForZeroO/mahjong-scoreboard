# 更合理的数据结构：兼顾即时计分与长期统计

## 一、目标

- **即时计分**：对局进行中写轮次分、改总分，响应快、事务简单。
- **长期查询**：按用户查「本月/本年」统计时，少扫表、少 JOIN、不解析 JSON，可扩展。

---

## 二、当前结构的不足（简要）

| 问题 | 影响 |
|------|------|
| 统计只能「按用户全量参与记录 + 内存按时间筛」 | 用户玩得越久，扫的 match_participants 越多，且需 JOIN matches 取 end_time/status |
| 胜负存于 match_results.total_scores JSON | 每次统计都要查 match_results 并解析 JSON，无法用 SQL 聚合 |
| 没有「按用户+时间」的专用数据 | 无法做单表范围查询，索引也难以针对「用户维度+时间」优化 |

---

## 三、推荐方案：保留现网主表 + 新增「用户对局结果汇总表」

思路：**对局进行中**沿用现有 `matches`、`match_participants`、`round_scores` 做即时计分；**对局结束时**多写一张「按用户、按场次」的汇总表，专门服务统计与历史查询。

### 3.1 主表保持不变（即时计分）

- **matches**：对局主表，`end_time`、`status`、`settlement_multiplier` 等照旧。
- **match_participants**：参与关系与当局总分，计分时只更新本表 + `round_scores`。
- **round_scores**：轮次得分，支撑实时计分与详情。
- **match_results**：保留，用于结果页展示（如 total_scores JSON）；统计逻辑不再依赖解析它。

即时计分流程不变：写/更新 `round_scores` → 汇总到 `match_participants.total_score`，必要时更新 `matches.total_rounds` 等。

### 3.2 新增：用户对局结果汇总表 `user_match_stats`

**用途**：每一场对局结束后，为**每个参与者**写一条记录，表示「该用户在该局的结果」；后续按用户、按时间查统计只读这张表即可。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGSERIAL PRIMARY KEY | 自增主键 |
| user_id | BIGINT NOT NULL | 用户标识，与现有接口一致（wechat_users.id） |
| match_id | BIGINT NOT NULL | 对局 ID |
| participant_id | BIGINT | 对应 match_participants.id，便于对账 |
| total_score | INTEGER NOT NULL | 原始总分（未乘倍率） |
| final_score | INTEGER NOT NULL | 倍率后最终得分 |
| settlement_multiplier | DOUBLE PRECISION NOT NULL DEFAULT 1 | 本局倍率 |
| is_winner | BOOLEAN NOT NULL | 是否获胜 |
| match_end_time | BIGINT NOT NULL | 对局结束时间戳（来自 matches.end_time） |
| create_time | BIGINT NOT NULL | 写入时间 |

**约束与索引**：

- `UNIQUE(user_id, match_id)`：同一用户在同一对局只一条。
- `FOREIGN KEY (user_id) REFERENCES wechat_users(id)`（或按你库实际主表调整）。
- `FOREIGN KEY (match_id) REFERENCES matches(match_id) ON DELETE CASCADE`。
- **核心查询索引**：`CREATE INDEX idx_user_match_stats_user_end_time ON user_match_stats(user_id, match_end_time);`

**写入时机**：在现有「收盘」逻辑里，在写 `match_results`、更新 `matches.status/end_time` 的同一事务中，根据本局每个 `match_participant` 计算 total_score、final_score、is_winner，插入 `user_match_stats`（并写入 match_end_time）。

这样：

- 即时计分：不碰 `user_match_stats`，只写 matches / match_participants / round_scores。
- 长期查询：「某用户某月/某年」= 在 `user_match_stats` 上按 `user_id` 和 `match_end_time` 范围做聚合，无需 JOIN matches、不解析 JSON。

### 3.3 可选：月度汇总表 `user_monthly_stats`

若希望「本月数据」接口极简、可缓存，可再加一张按月的预聚合表：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGSERIAL PRIMARY KEY | |
| user_id | BIGINT NOT NULL | |
| year_month | INTEGER NOT NULL | 格式 YYYYMM，如 202503 |
| total_matches | INTEGER NOT NULL DEFAULT 0 | 总场次 |
| win_matches | INTEGER NOT NULL DEFAULT 0 | 胜场 |
| lose_matches | INTEGER NOT NULL DEFAULT 0 | 负场 |
| total_score | INTEGER NOT NULL DEFAULT 0 | 总得分（未乘倍率） |
| total_multiplier_score | DOUBLE PRECISION NOT NULL DEFAULT 0 | 总倍率分 |
| win_total_score | INTEGER NOT NULL DEFAULT 0 | 胜场总得分 |
| win_total_multiplier_score | DOUBLE PRECISION NOT NULL DEFAULT 0 | 胜场总倍率分 |
| lose_total_score | INTEGER NOT NULL DEFAULT 0 | 负场总得分 |
| lose_total_multiplier_score | DOUBLE PRECISION NOT NULL DEFAULT 0 | 负场总倍率分 |
| update_time | BIGINT NOT NULL | 最后更新时间 |

- `UNIQUE(user_id, year_month)`，主键或唯一索引。
- 对局结束时：根据该局 `user_match_stats` 的几条记录，更新（或插入）对应 `user_id` + 当月的 `user_monthly_stats` 行（累加场次、得分等）。
- 「本月数据」= 按 `user_id` + 当前年月查一行，必要时再做短期缓存。

---

## 四、数据流小结

```
对局进行中（即时计分）：
   round_scores 写入/更新
   → match_participants.total_score 汇总
   → matches 状态/轮次 更新
   （不写 user_match_stats / user_monthly_stats）

对局结束（收盘）：
   matches.status=1, end_time, settlement_multiplier 更新
   match_results 写入（含 total_scores JSON，供结果页展示）
   → 新增：为每个参与者写入 user_match_stats（含 match_end_time）
   → 可选：更新 user_monthly_stats 对应年月行

长期统计（本月/本年）：
   方案 A：只加 user_match_stats
     → 按 user_id + match_end_time 范围聚合（单表 + 索引）
   方案 B：再加 user_monthly_stats
     → 本月：查 user_monthly_stats 一行；本年：按 12 行或仍从 user_match_stats 聚合
```

---

## 五、索引与维护建议

- **matches**：`(status, end_time)` 复合索引，便于按时间范围查已完成对局（若尚未有则建议加）。
- **user_match_stats**：必须有的索引为 `(user_id, match_end_time)`；若按 match 反查可再加 `match_id`。
- **user_monthly_stats**：`(user_id, year_month)` 唯一即主查索引。

历史数据：若在已有库上新增 `user_match_stats`，可通过一次性脚本从现有 `match_results` + `match_participants` + `matches` 反算并回填（只处理 status=1 且 end_time 非空的对局）；回填完成后再切统计逻辑到新表。

---

## 六、总结

| 维度 | 做法 |
|------|------|
| 即时计分 | 保持现有 matches / match_participants / round_scores 结构与写路径 |
| 长期查询 | 新增 user_match_stats（必选），按 user_id + match_end_time 做范围聚合；可选 user_monthly_stats 做月度预聚合 |
| 数据管理 | 结果明细仍保留在 match_results；统计口径统一来自 user_match_stats（及可选 user_monthly_stats），便于扩展和缓存 |

这样在不大改现有计分流程的前提下，长期统计可以单表、索引友好、易扩展，同时方便做缓存与后续数据分析。
