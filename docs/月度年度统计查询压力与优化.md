# 按用户查询「一个月 / 一年」对局数据：压力分析与优化方案

## 一、当前实现方式简要回顾

- **接口**：`POST /api/v1/statistics/users/{wechatUserId}/monthly`，请求体 `{ year, month }`，`month` 为空时表示**全年**。
- **实现**：`StatisticsServiceImpl.getMonthlyStatistics(wechatUserId, year, month)`。

核心步骤：

1. 根据 `wechatUserId`（实为 wechat_users 主键 id）查 `WechatUser`。
2. **查该用户全部参与记录**：`participantRepository.findByUser(wechatUser)` → 无时间条件，拉取该用户所有 `MatchParticipant`。
3. **在内存中按时间与状态过滤**：遍历每条参与记录，用 `participant.getMatch()` 取对局，再根据 `match.getEndTime()` 是否在 [startTimestamp, endTimestamp] 且 `match.getStatus() == 1` 过滤。
4. **N+1 查 MatchResult**：对每个在时间范围内的对局，再调 `matchResultRepository.findByMatchId(match.getMatchId())`，解析 `total_scores` JSON 判断胜负。
5. **算「最高/最低分玩家」**：`matchRepository.findCompletedMatchesByTimeRange(start, end)` 得到该时间段内所有已完成对局，再对每个对局 `participantRepository.findByMatch(match)` 拉参与者并聚合。

## 二、是否存在压力？

### 2.1 数据量级（经验值）

| 维度       | 一个月 | 一年   |
|------------|--------|--------|
| 单用户场次 | 约 20~60 | 约 200~700+ |
| 全平台该时段对局数 | 视运营规模，可能数百～数千 | 数千～数万 |

### 2.2 当前实现的压力点

| 问题 | 影响 | 一个月 | 一年 |
|------|------|--------|------|
| **findByUser 全量** | 每次都拉该用户**全部**历史参与记录，再在内存里按时间筛。用户玩得越久，数据越大。 | 若总参与数 < 几百，一般还能接受 | 总参与数到几千时，会拉很多无用数据，内存与 DB 都浪费 |
| **Match 懒加载** | 遍历 participant 时 `getMatch()` 可能触发逐条查 match。 | 几十次查询 | 几百次查询 |
| **MatchResult 的 N+1** | 每个在时间范围内的对局都查一次 match_results 并解析 JSON。 | 几十次查询 + JSON 解析 | 几百次查询 + JSON 解析 |
| **最高/最低分玩家** | 先查时间段内**全部**已完成对局，再对**每场** `findByMatch` 取参与者。 | 若该时段对局多，参与者也多，查询次数 = 1 + 该时段对局数 | 全年时该时段对局数很大，N+1 明显 |

结论：

- **只查一个月**：在「单用户总参与数」还不大（例如 < 500）时，多数场景可以跑，但已有不必要的全量拉取和 N+1。
- **查一年**：同一实现会明显变重，**不能算无压力**；用户或平台对局量上去后，延迟和 DB 负载都会上来。

所以：**以当前数据结构和实现方式，一个月在数据量较小时尚可接受，一年或数据量增大后会有压力，建议做优化。**

## 三、优化方案（在现有表结构下即可做）

### 3.1 在数据库层按「用户 + 时间范围」过滤（优先）

**思路**：不再 `findByUser` 全量再在内存里筛，而是**按用户 + 对局结束时间**在 DB 一次查完该时间段内的参与记录。

- 在 `MatchParticipantRepository` 增加方法，例如：

```java
@Query("SELECT p FROM MatchParticipant p JOIN FETCH p.match m " +
       "WHERE p.user = :user AND m.status = 1 " +
       "AND m.endTime >= :start AND m.endTime <= :end")
List<MatchParticipant> findByUserAndMatchCompletedInTimeRange(
    @Param("user") WechatUser user,
    @Param("start") Long startTimestamp,
    @Param("end") Long endTimestamp);
```

- 统计逻辑里：用上述方法替代「findByUser + 内存过滤」，并继续用当前方式算总分、胜场、负场、倍率分等。
- **效果**：一个月/一年只扫该时间段内的参与记录，数据量小一个数量级；`JOIN FETCH p.match` 避免 Match 的 N+1。

**注意**：若 `wechatUserId` 实际用的是 wechat_users 主键 id，这里 `p.user` 即 WechatUser 主键关联，与当前用法一致。

---

### 3.2 消除 MatchResult 的 N+1

**思路**：当前对「时间范围内的每个 match_id」都调一次 `findByMatchId`。可改为批量查询 + 内存映射。

- 在 `MatchResultRepository` 增加：

```java
List<MatchResult> findByMatchIdIn(List<Long> matchIds);
```

- 在统计逻辑中：
  - 先由「用户 + 时间范围」得到 `List<MatchParticipant>`，再抽出 `matchIds`。
  - 一次调用 `findByMatchIdIn(matchIds)`，得到 `List<MatchResult>`。
  - 在内存里做成 `Map<Long, MatchResult>`，后续按 matchId 取用并解析 `total_scores` 判断胜负。

**效果**：从「每场 1 次 DB + 1 次 JSON 解析」变为「1 次批量查询 + 多次内存查找和解析」，查询次数从 N 降到 1。

---

### 3.3 最高/最低分玩家的计算方式

**思路**：当前是「该时间段内所有已完成对局 → 每场再查参与者」导致 N+1。可改为一次按「时间段内已完成对局」JOIN 参与者，在 DB 聚合（或应用层一次拉取后聚合）。

- 例如在 Repository 层用 JPQL 或原生 SQL，按 `matches.status = 1 AND end_time BETWEEN :start AND :end` 关联 `match_participants`，按 `user_id` 分组，对 `total_score * COALESCE(settlement_multiplier,1)` 做 SUM，再在应用层取最大/最小各一条（或 DB 用窗口函数/ORDER BY + LIMIT 取 top1/bottom1）。
- 若暂时不改 SQL，也可先 `findCompletedMatchesByTimeRange`，再**批量**查参与者：  
  `participantRepository.findByMatchIn(matches)`（需在 Repository 增加 `findByMatchIn(Collection<Match> matches)`），避免每场一次查询。

**效果**：大幅减少「按对局数 N 再查 N 次参与者」的 N+1，一年数据时收益明显。

---

### 3.4 索引（在现有结构上补强）

- **matches**：若尚未有，建议增加 `(status, end_time)` 复合索引，便于「已完成 + 时间范围」的查询（当前 `findCompletedMatchesByTimeRange` 及上面按时间范围的 JOIN 都会用到）。
- **match_participants**：已有 `user_id` 单列索引即可支持「按用户 + JOIN matches 按时间」的查询；若后续有「仅按 match_id 列表批量查参与者」的需求，现有 `match_id` 索引一般足够。

---

### 3.5 可选：短期缓存

- 对「本月数据」「本年数据」这类结果可做 5～10 分钟缓存（按 `wechatUserId + year + month` 为 key），减少重复计算。
- 适合读多写少、对实时性要求不高的统计页；若需要准实时，可缩短 TTL 或不做缓存。

---

## 四、小结

| 项目 | 结论 |
|------|------|
| **当前能否无压力？** | 一个月在数据量较小时尚可；一年或数据量增大后**有压力**。 |
| **建议优先做** | ① 按用户+时间范围在 DB 查参与记录（替代 findByUser 全量）；② MatchResult 批量查询去 N+1；③ 最高/最低分玩家一次聚合或批量查参与者。 |
| **表结构** | 现有 `matches`、`match_participants`、`match_results`、`wechat_users` 即可支持上述优化，无需改表结构；仅建议为 `matches(status, end_time)` 加复合索引。 |

按上述方式改造后，「按用户查一个月/一年数据」的查询量和延迟都会明显下降，可视为在现有结构下的较优方案。
